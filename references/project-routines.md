# 已确认的项目惯例

更新时间：2026-11-21

## jkm-fz-data

- 后端为 Flask + SQLAlchemy + MySQL，前端为原生 HTML/CSS/JavaScript，调度和 worker 分进程。
- 先阅读仓库 `AGENTS.md`；生产五进程、worker 节点隔离、短事务边界、任务心跳和权限树是既有约束。
- 数据库 schema 使用项目自研 init-db 同步，不用 Alembic；涉及表结构时先在测试库核对，再做生产发布。
- 调度任务只进入 `JOB_REGISTRY`；复杂业务放 service，蓝图保持轻量。
- 常规提交前至少执行仓库规定的 `git diff --check` 和 Python `compileall`，再做受影响功能验证。

## jkm-bi

- 主要页面是原生静态 HTML，AI 生图服务在 `gpt-image-api/`，本地 WSL 服务端口通常为 3810，CRM/API 通常为 8080。
- 生图任务数据和图片属于运行数据，不提交；代码更新前检查任务队列，发布时避免中断正在生成的任务。
- 生图上传文件和结果按任务 ID 保存在服务的 `data/images/`，任务记录在 `data/tasks.json`；保留策略以当前代码为准。
- 生图提示词应按 workflow 隔离；自定义模板保留用户明确要求，包装裂变等多图任务使用稳定的索引方向，重试时保持同一方案。
- 前端页面调整要同时检查页面脚本语法、交互错误位置、服务端边界校验和实际 API 返回。
- `main` 是稳定发布分支；用户明确要求时才合并/推送到它。生产发布前备份变更文件、核对远端提交并检查 `jkm-bi.service` 与 `jkm-bi-image.service`。

## 跨平台业务开发模式

- 平台差异要落在平台适配层，统一业务流程复用共享 service；需要补齐行为时优先参考已有平台的真实实现和接口证据。
- 采集、保活、上传和异步生成类任务要有状态、心跳、重试、幂等和可追溯日志；一次失败不应阻断可继续处理的正常记录。
- 数据不完整时区分可人工补正字段与必须阻断字段；支持在原任务上下文继续核对和生成，避免重复任务和重复业务数据。
- 前端错误应靠近触发控件显示，提示使用业务语言；列表要展示来源、模板、状态、数量和结果，便于排查。
- 外部平台请求要保留足够的请求阶段、响应状态和错误上下文供排障，但按当前项目的脱敏和凭据规则处理敏感内容。
- 自动化功能要同时验证本地、测试和生产边界，不能用生产账号或运行数据替代测试验证。
